================================================================================
                        IF CONFLICT HAPPENS (UNLIKELY)
================================================================================

Conflict would happen if:
1. Someone else edited src/database/postgres_client.py (unlikely, it's your file)
2. You both edited src/utils/embedding_utils.py (unlikely, it's your file)
3. Changes to shared files like requirements.txt

IF THIS HAPPENS:

Step 1: See what happened
$ git status

Step 2: Look at the conflict
$ git diff

Step 3: Talk to Rohan
Ask him who else edited this file and coordinate

Step 4: Fix it
Either keep your version or theirs, or merge both
$ git add fixed_file.py
$ git commit -m "[backend] merge: resolve conflict with [other person]"

Step 5: Push
$ git push origin feature/backend-rag-apis

================================================================================
                        COMMUNICATION = NO CONFLICTS
================================================================================

BEFORE EDITING SHARED FILES, ASK ROHAN:

- .env.example changes? Ask first

  Ask Rohan first!

GOOD EXAMPLE:
"Hey Rohan, I need to add 'pgvector>=0.3.0' to requirements.txt"
→ Rohan adds it to develop
→ You pull it
→ No conflict!

BAD EXAMPLE:
You add it directly to requirements.txt on your branch
→ Others add different packages to develop's requirements.txt
→ CONFLICT when merging!

================================================================================
                    COMMIT MESSAGE CONVENTION
================================================================================

Format: [backend] action: description

Examples (GOOD):
✓ [backend] feat: implement postgres connection pool
✓ [backend] test: add database tests
✓ [backend] fix: handle API errors
✓ [backend] refactor: optimize queries

Examples (BAD - AVOID):
✗ "fix" - not descriptive
✗ "WIP" - work in progress, push complete work
✗ "[ml-nlp] feat: ..." - wrong prefix, you're [backend]
✗ "Updated stuff" - not clear what

GOOD commits = CLEAR history = EASY merges
